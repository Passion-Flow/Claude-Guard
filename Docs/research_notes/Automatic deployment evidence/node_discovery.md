# Automatic Shadowrocket node discovery and userspace Tailscale binding

Read-only investigation on 2026-11-12. Scope: repository, installed public bundle metadata, preference **key names/types**, SQLite **schemas**, process/socket identity metadata, and primary documentation. No profile rows, node credentials, subscription URLs, encryption-key values, keychain contents, deployment IPs, UI actions, installations, privileged prompts, or networking configuration changes were captured. The only local socket connection exchanged no HTTP payload.

## Can the selected Shadowrocket node and its verification settings be discovered reliably?

### Takeaway
No complete, documented mechanism was found that lets an unrelated Guard app retrieve Shadowrocket's selected endpoint plus TLS/REALITY verification settings. Automatic tunnel identification and socket candidate discovery are feasible; automatically declaring one candidate secure would exceed the evidence.

### Cited Findings
- `NETunnelProviderManager.loadAllFromPreferences` reads configurations created by the **calling app**. Apple also requires the Network Extension entitlement. This is not a cross-vendor profile API; adding an entitlement or running as root does not make Guard the creating app. `sendProviderMessage` belongs to that app's provider session, not a documented Shadowrocket query protocol. — [Apple manager documentation](https://developer.apple.com/documentation/networkextension/netunnelprovidermanager?language=objc); [installed SDK manager header](/Library/Developer/CommandLineTools/SDKs/MacOSX.sdk/System/Library/Frameworks/NetworkExtension.framework/Headers/NETunnelProviderManager.h); [session header](/Library/Developer/CommandLineTools/SDKs/MacOSX.sdk/System/Library/Frameworks/NetworkExtension.framework/Headers/NETunnelProviderSession.h)
- The inspected Shadowrocket packet extension identifies as `com.liguangming.Shadowrocket.PacketTunnel`; both app and extension declare `group.com.liguangming.Shadowrocket`. Public URL-scheme registration provides import/control entry points, not a documented selected-node response schema. — [installed app metadata](/Applications/Shadowrocket.app/Contents/Info.plist); [installed provider metadata](/Applications/Shadowrocket.app/Contents/PlugIns/MacPacketTunnel.appex/Contents/Info.plist)
- The shipped intent definition contains StartTunnel, StopTunnel, ToggleTunnel, GlobalRouting, CronScript and UpdateSubscription. Its response schemas contain success/failure/connection-state codes, with no endpoint or TLS/REALITY fields. These are schema observations, not executed actions. — [installed intent definition](/Applications/Shadowrocket.app/Contents/Resources/Base.lproj/Intents.intentdefinition)
- The shared preferences expose key names `group.com.liguangming.SelectedServerUUID`, `SelectedServerName`, `GlobalRoutingMethod`, and `NetworkDataEncryptionKey.v1` (same prefix). Names alone neither locate the selected endpoint nor establish certificate verification. A zero-byte `ServerManager.state` supplied no record schema. No values were extracted. — [local shared-container metadata](https://developer.apple.com/documentation/security)
- Schema-only inspection found shared `rule.db` tables for rules, hosts and CIDRs; main-app `Documents/Databases/default.db` contains generic FTS3 `config(section,name,value,option,ext,remarks,created)` plus FTS backing tables. Neither schema supplies a documented selected-server-to-endpoint/security relation. Main preference `DLWModuleManager` is a list, with no values or nested user content inspected. — [shared database location](https://developer.apple.com/documentation/security); [main database location](https://developer.apple.com/documentation/security)
- Current endpoint detection first requires a user-entered IPv4 address, checks the provider executable's static signature, and samples its sockets. Removing that address filter produces candidates, not selected-node evidence. A live provider can have many remote sockets; socket count alone does not identify the selected node. — [EndpointDetection.swift](../../Sources/EndpointDetection.swift); [GuardModel.swift](../../Sources/GuardModel.swift)
- Current admission accepts supported share-link declarations, rejects insecure flags, and binds declarations to an endpoint. The root `.trial` path additionally requires `route.matches(nodeLink)`. A discovered socket cannot replace those declarations without changing the trust contract. — [NodeAdmission.swift](../../Sources/NodeAdmission.swift); [GuardService.swift](../../Sources/GuardService.swift); [GuardianCore.swift](../../Daemon/GuardianCore.swift)

### Inferences
- Implement automatic **candidate discovery** with explicit states: unavailable, ambiguous, endpoint observed, configuration security unknown, and admitted. Never synthesize `security=tls`/REALITY from TCP, port 443, provider signature, traffic volume, or a successful unrelated HTTPS probe.
- Identify the VPN service/provider and current `utun` through SystemConfiguration, cross-check the default route, and invalidate on service/process/interface changes. `SCNetworkConnectionCopyExtendedStatus` documents connection/subcomponent status, not a third-party selected proxy's TLS verifier. The supplied current observation already establishes that this Shadowrocket instance reports loopback as its server address. — [SDK status contract](/Library/Developer/CommandLineTools/SDKs/MacOSX.sdk/System/Library/Frameworks/SystemConfiguration.framework/Headers/SCNetworkConnection.h)
- A reliable fully automatic path needs vendor cooperation: a documented read-only selected-node export containing stable selection ID/generation, numeric outer endpoint, transport, encryption mode, verification enabled, expected server identity/pins, and supported REALITY validation metadata. Bind it to the live signed provider and observed tuple, then retain existing exit/risk admission. An imported declaration still does not prove a live handshake.
- Preference UUIDs could invalidate cached evidence after selection changes, but are untrusted, undocumented hints. Selection may also differ from the actual route when rules, groups, fallback, chaining, domain resolution, or port hopping are involved. Do not broaden the PF allowlist to compensate for ambiguity.

### Gaps
- No supported selected-node/security export was found on the vendor website linked by the App Store, or in the shipped intent schema. This is a bounded negative result, not proof that no private mechanism exists. Do not use unrelated websites that brand themselves “official” as vendor API evidence. — [App Store vendor link](https://apps.apple.com/us/app/shadowrocket/id932747118); [actual vendor website](https://shadowlaunch.com/)
- Node/profile row decoding, encrypted storage analysis, private provider messaging, memory inspection, and UI reading were outside this task. No claim is made that the generic database contains no node data; its schema alone cannot establish a safe supported extraction.

## What privileges and native APIs does safe discovery require?

### Takeaway
Keep observation in the logged-in user's process; current same-user process/socket inspection worked without elevation. Reading another app's private container has a separate privacy-authorization boundary and does not solve the missing semantic/API contract.

### Cited Findings
- On macOS 15+, nonmember access to app/group containers results in a user authorization prompt. Different developer teams cannot share the same app group, and `group.` membership requires provisioning. Guard cannot legitimately add Shadowrocket's app-group entitlement to obtain silent access. — [Apple app-group access](https://developer.apple.com/documentation/xcode/accessing-app-group-containers.md); [Apple container protection](https://developer.apple.com/documentation/xcode/protecting-local-app-data-using-containers.md)
- Darwin exposes `PROC_PIDLISTFDS`/`PROC_PIDFDSOCKETINFO` and IPv4/IPv6 socket structures, allowing native socket enumeration rather than parsing command output. Code Signing Services supports obtaining a **running** guest by PID/audit attributes. — [installed libproc structures](/Library/Developer/CommandLineTools/SDKs/MacOSX.sdk/usr/include/sys/proc_info.h); [Apple running-code API](https://developer.apple.com/documentation/security/seccodecopyguestwithattributes(_:_:_:_:)); [guest attributes](https://developer.apple.com/documentation/security/guest-attribute-dictionary-keys)

### Inferences
- For this same-UID provider, use native process identity plus socket enumeration, bounded counts/timeouts, and PID-generation/start-time checks. Validate the running code's designated requirement, not merely a pathname returned by `ps`. Recheck identity around enumeration; treat exit, permission denial, unsupported socket state or multiple candidates as unknown.
- No admin authorization was needed for the observed same-user `ps`/`lsof`, static code metadata or Unix-peer identity checks. Cross-UID/root-owned process visibility can require a privileged observer; do not assume this same-user success covers a different deployment. No root process inspection was attempted.
- Container reading may need explicit user privacy authorization on a deployed Guard build even though this existing research context could inspect metadata. Administrative PF approval is not evidence that cross-app data access is authorized. Do not request Full Disk Access or bypass protections merely to chase an undocumented format.
- Keep any future permitted parser in the user process, allowlist only non-secret fields, bound input sizes, reject duplicate/unknown settings, never persist whole profiles, and pass a typed minimal observation through authenticated XPC. Root must validate source/freshness/binding rather than accept a GUI-generated security label.

### Gaps
- The current research process's prior privacy grants and the eventual Guard app's TCC behavior were not audited. No new privacy or administrator prompt was requested. Sandbox and older macOS variations need target acceptance.

## How should Guard bind the current userspace Tailscale safely?

### Takeaway
Use native HTTP over the existing Unix socket from the user process, with peer-credential/process binding; never execute `~/.local/bin/tailscale` or `tailscaled` as root. This installation is explicitly `--tun=userspace-networking`, so it has no Tailscale tunnel interface to attach to the existing separate-tunnel SSH exception.

### Cited Findings
- Local metadata shows user-owned `~/.local/bin/tailscaled` and `tailscale`. The daemon is ad-hoc/linker signed with no TeamIdentifier. A userspace deployment can declare `--tun=userspace-networking`. A payload-free Unix-socket connection identified the live daemon's current UID/PID using `getpeereid` and `LOCAL_PEERPID`. The socket is `~/.local/state/tailscale-userspace/tailscaled.sock`, mode 0666; filenames and mode are observations, not a provenance guarantee. — [local launch metadata](https://developer.apple.com/documentation/security); [Darwin peer-identity definitions](https://raw.githubusercontent.com/apple-oss-distributions/xnu/main/bsd/sys/un.h)
- Tailscale's native client supports an explicit socket and socket-only operation. `Status` and `StatusWithoutPeers` are documented stable client APIs; the latter requests `/localapi/v0/status?peers=false`. Unix LocalAPI connections receive read permission, while mutation permission is separately determined. — [Tailscale LocalAPI client](https://raw.githubusercontent.com/tailscale/tailscale/main/client/local/local.go); [LocalAPI permission logic](https://raw.githubusercontent.com/tailscale/tailscale/main/ipn/ipnserver/server.go); [status handler](https://raw.githubusercontent.com/tailscale/tailscale/main/ipn/localapi/localapi.go)
- Status includes `TUN` (false means userspace), `BackendState`, assigned addresses and peer metadata. It also includes `AuthURL`; **never log/store/forward a raw status response**. No live status HTTP request was made during this investigation. — [Tailscale status schema](https://raw.githubusercontent.com/tailscale/tailscale/main/ipn/ipnstate/ipnstate.go)
- Userspace mode supplies SOCKS5/HTTP proxy functionality instead of creating a VPN tunnel device. Tailscale's 0666 socket permission is intentional on peer-credential platforms. — [official userspace networking documentation](https://tailscale.com/docs/concepts/userspace-networking); [socket permissions source](https://raw.githubusercontent.com/tailscale/tailscale/main/safesocket/unixsocket.go)

### Inferences
- Discover the current owner's daemon and socket through process/file-descriptor metadata. On each connection require peer UID to equal the configured owner; obtain `LOCAL_PEERTOKEN` where available and bind the running process with Code Signing Services, otherwise use PID plus generation checks. Use only bounded read-only GETs and allowlisted decoded fields; reject redirects, network fallback and unexpected schemas. Rebind after daemon restart or socket replacement.
- This authenticates **which local process answered**, not trusted Tailscale provenance: an owner-controlled ad-hoc binary can be replaced or impersonated by that owner. Its status must not independently authorize a root physical-network exception. No root subprocess, shell, LaunchAgent, or user-writable executable is necessary for observation.
- Distinguish userspace and kernel-tunnel Tailscale in the product. For userspace, retain the physical block and require outer sockets to follow the already approved Shadowrocket route; never invent a `utun` or add LAN/DERP/control bypass. Existing “one peer, SSH only, separate tunnel” enforcement cannot be claimed for arbitrary traffic inside a userspace proxy without an additional peer/port-aware broker or equivalent controls. Keep that feature unavailable until implemented and packet-tested.

### Gaps
- Runtime status content, peer selection, proxy listeners and live underlay behavior were intentionally not queried/modified. A Unix-peer identity check alone does not demonstrate that actual Tailscale transport uses Shadowrocket, or that only one peer/SSH is accessible.
