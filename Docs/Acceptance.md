# Development-machine acceptance

This checklist is for a local operator using the matched private installer. Offline fixtures and compilation do not prove real network enforcement. Do not sign in to a protected service until the required tests pass. Record PASS, FAIL or NOT TESTED for every item. Keep node addresses, account identifiers, API keys and packet payloads out of shared reports.

## Preparation

1. Keep a local keyboard and display available. Save work and close protected applications. A cloud-connected coding assistant can lose its connection during fault injection.
2. Verify the supplied SHA-256 checksums. Open the disk image and run the private installer. Complete administrator authorization yourself. Use Apple's per-file **Open Anyway** action only for the build you reviewed; never disable Gatekeeper or SIP.
3. Open the single Claude Guard application. Confirm the guardian is installed, both languages work, system/light/dark appearance works and selection controls are usable with keyboard and mouse.
4. Connect the intended Shadowrocket node. Let Guard discover its supported metadata, endpoint, tunnel and exit automatically. The default keyless policy requires Residential, risk at most 10, clear risk flags and the approved region. Missing fields, quota errors and unavailability cannot approve release. A provider score is an estimate, not an account eligibility guarantee.
5. If needed, set one Tailscale IPv4 SSH peer in the private 100.64.0.0/10 range. Keep Tailscale connected. Guard adds no direct LAN, DERP or control-plane exception. The outer Tailscale transport must work through Shadowrocket. Subnet routing, exit-node mode, general LAN access and non-SSH peer ports are not supported by this exception.
6. Locate **Open offline recovery** in Claude Guard and the matching **OfflineRecovery.pkg** and **Uninstall.pkg** in the image before testing. Recovery restores direct connectivity if the VPN is absent. Keep protected applications closed during restoration.

## Required evidence

The coding assistant may prepare bounded local observation commands or scripts; the user must not type commands. Computer Use should operate the installer, Shadowrocket, Wi-Fi, browser and Guard. Passwords and API keys remain user-entered and must not be recorded. A browser error alone is not proof: packet captures on every physical interface, PF readback and fresh requests are needed. Capture headers/metadata only, store evidence locally and redact before sharing.

| Scenario | Expected behavior |
| --- | --- |
| Automatic activation | Physical direct traffic is blocked before validation; at least six successful exit observations spanning 15 seconds and fresh accepted risk evidence precede OPEN. Existing connections reset once. |
| VPN off, then on | Fresh IPv4/IPv6, DNS, UDP/QUIC and browser requests cannot bypass to a physical interface. The fixed node can reconnect. Recovery completes a new stability window before OPEN. |
| Local Wi-Fi off, then on | No probes or reconnect storm while the underlay is absent. DHCP and fixed-node bootstrap recover when the link returns. A stale Connected service is recycled once. Applications remain blocked until revalidated. |
| Ethernet and route changes | The old physical exception is removed. New physical routes never become general bypasses. Route changes force revalidation. Include more-specific routes and a second tunnel. |
| Wrong exit and risk failure | A different exit, wrong region, rejected or missing risk evidence cannot produce OPEN. Verify malformed responses and expired evidence with fixtures; use an authorized test account for live provider checks. |
| Pause and resume | Pause blocks ordinary traffic while retaining configuration. Resume requires fresh risk evidence and a stability window. It does not temporarily restore direct traffic. |
| Dashboard quit | The guardian keeps enforcing and reporting. Reopening the application retrieves root-owned state. |
| Worker failure | Terminate and separately force-kill only the known Guard worker. Rules remain restrictive and supervision creates a new session. A prior OPEN observation is not reused. |
| PF tampering | Removing Guard rules or disabling PF is detected and repaired, states are cleared and recovery revalidates. Measure and record the interval where PF was disabled; do not report zero exposure. Never replace unrelated PF rules. |
| Legacy trial timeout (fixture only) | Without confirmation, the 60-second trial removes Guard rules and restores normal networking. Keep protected apps closed. Continuing the trial enables persistent protection. |
| Sleep and wake | Observe sealing before sleep acknowledgment, including a sleep shorter than the identity lease. Completed wake creates a new worker/session and requires fresh identity/stability/risk admission. Early or duplicate wake does not resume twice. Repeat with paused and upgrade intent, a pending old writer and explicit restore during suspension. The original service recovers; foreign retained PF rules are rejected. PF errors remain reported failures, not proof of successful sealing. |
| Restart | Confirm persistent intent, restrictive startup and fresh admission. Capture from before login where feasible and report the interval before the guardian enforces. A LaunchDaemon alone cannot prove zero early-boot exposure. |
| Tailscale SSH | SSH to the selected peer works only after OPEN. Closing the VPN interrupts new and existing peer traffic. The physical capture shows no Tailscale direct transport or LAN bypass. Restore the VPN and verify SSH after fresh admission. |
| Browser WebRTC | Under continuous protection, use a new PeerConnection in the actual browser for protected, blocked and recovered phases. Distinguish private/mDNS, public host, server-reflexive and relay evidence. Close the test page before restoring direct networking. Empty results remain unverified. |
| Anonymous service path | Explicitly check the fixed service trace endpoints without account cookies. Verify redirects, missing endpoints and invalid bodies remain unverified, that results expire, and that loss of protection cancels the check. The result must never authorize traffic or claim a signed-in browser's path. |
| Offline recovery | With the VPN disconnected and the main daemon unavailable, recover using the separate application/channel or matching recovery package. Also test a stopped primary holding the control lock: independent recovery must stop the primary before taking that lock. Verify rule removal and durable disarming; protection must not re-arm afterward or after reboot. |
| Upgrade and uninstall | Upgrade while protected enters a sealed maintenance state until explicit Resume. A failed upgrade cannot silently clear protection. Uninstall disarms, restores, stops both jobs and removes only Guard-owned components. |
| Resources and reports | Observe idle CPU, memory, check frequency and event growth. No overlapping checks or persistent browser tests. Exported reports contain no node credentials, API keys, candidate addresses or raw packet data. |

## Optional development operator prompt

> Validate Claude Guard on this Mac from the matched private installation image and its checksum file. Read Installation.md and this acceptance checklist first. Do not assume compilation means network safety. Use Computer Use for GUI actions and local tooling only where packet evidence requires it; do not make me type commands. I will enter passwords in system fields. Do not read or record their values. Close protected apps before the trial, automatic trial restoration, recovery, upgrade and uninstall. Keep a local offline recovery path ready. First inspect the current routes, interfaces, existing PF owners and installed Guard version without changing them. Install the matched package; allow ordinary per-file Gatekeeper and administrator prompts, but do not disable system security or install unrelated runtimes. Perform each checklist scenario, collecting minimal local packet-header/PF evidence. Before disconnecting the VPN or Wi-Fi, prepare a bounded local sequence that reconnects it even if this assistant loses cloud access; do not rely on a later cloud tool call to restore it. Do not flush or alter unrelated system rules. Stop a test immediately if unexpected direct application packets appear or recovery fails, retain restrictive rules and report the actual failure. Do not access real Claude accounts as a probe. Redact addresses, keys and identifiers in shared output. Produce a table of PASS/FAIL/NOT TESTED, evidence paths, measured recovery times, PF-disabled/early-boot gaps and unresolved risks. Never label unobserved scenarios as passing. Leave the agreed protected state active only after successful checks; otherwise keep apps closed and explain the safe local recovery action.

## Known architecture limits

PF is shared administrative machinery, not an Apple-supported application API. Root software can disable it. Guard cannot guarantee protection before its startup job runs or during the interval between disabling PF and repair. PF cannot distinguish a node connection created by Shadowrocket from another process connecting to that same numeric address and port. Use a dedicated node and measure these gaps. If an acceptance requirement is zero exposure across those intervals, this PF edition does not meet it; changing UI, encryption terminology or adding more PF anchors cannot establish that guarantee.

## Deployment distinction

This matrix belongs to development-machine verification, not a mandatory manual checklist for every target. The target installer starts automatic discovery and admission. Record unperformed scenarios honestly; successful installation on one host cannot certify every network, hardware generation or reboot transition.
